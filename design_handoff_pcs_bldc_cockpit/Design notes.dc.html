pcs_bldc cockpit · design system note

A warm instrument, not a consumer dashboard

The Organic system supplies the type, the radii and both accents. The only departure is the ground: a bench tool lives in a dim workshop, so the cream ground is inverted onto the warm dark end of the same neutral ramp. Everything else — Caprasimo over Figtree, terracotta and sage, 16px radii growing into pills — is used as specified.

Below is what a new surface should reach for. Anything not listed here should be derived from the ramps in styles.css rather than invented.

Only two accents carry meaning, and they carry it consistently: sage = the device agrees with us, terracotta = attention or the live cursor. There is deliberately no red. A refusal or a mismatch is not a crash — the board is doing its job — so the terracotta accent, at higher border weight, does the raising. Reserve any future red strictly for a latched hardware fault.

Trace colours

#f6a06b #aebf92 #e0c46a #86b8c4 #d98a9c #c9c1b4

A six-colour cycle, assigned in order as signals are added to a plot and remembered per signal so a trace keeps its colour when it moves between widgets. The first two are the system accents; the remaining four are held at the same OKLCH lightness (~0.78) so no trace visually outweighs another. Beyond six, repeat the cycle with a dashed stroke rather than adding hues.

Organic has no monospace voice, so the system gains one: the platform stack (ui-monospace, Menlo, Consolas), no download needed. The rule that makes it feel intentional rather than bolted on: every machine-authored string is mono, every human-authored string is Figtree or Caprasimo. Values, symbol names, hashes, timestamps, ports, units — mono, tabular, right-aligned in columns. Labels, prose, buttons — the Organic faces. Caprasimo appears only as a title; it never sits next to a number.

Spacing, radius, elevation

Organic's density (4.4 / 8.8 / 13.2 / 17.6 / 26.4) rounded to the instrument grid: 4 · 6 · 8 · 12 · 16 · 20. Widget padding 12, row padding 6/8, gutter between widgets 12, window padding 12–16. Rows are 26–30px tall — dense enough to read forty signals, loose enough that the rounded shapes still breathe.

Radii step down as things get smaller and more functional: widget 20, dialog 26, card/meter 16, plot canvas 10, row 12, everything pill-shaped that is a control. The plot canvas keeps the smallest radius on purpose — it is the one hard-edged surface in the app, and its squareness reads as "this is the measurement."

One elevation for floating widgets (0 3px 14px rgba(0,0,0,.32)), one for overlays and dialogs (0 14px 40px rgba(0,0,0,.55)), plus the 1px rgba(238,231,219,.1) hairline every surface carries. On a dark ground the hairline does most of the separating; the shadow only says "this floats and can be dragged."

Themes

Every value above is a custom property, so a theme is a token block and nothing else — no per-component overrides. Three ship: Warm (the Organic ground, default), Graphite (cool grey, cyan accent) and Neon (near-black, magenta accent). Selector sits at the right end of the connection bar; the theme is set as data-theme on the document root.

--ink-*the five surfaces: bg, chrome, surface, raised, well — plus hint and warn
--*-rgbtriples for the alpha overlays (hairlines, scrims, tints) so rgba(var(--hair-rgb),.1) retints per theme
--r-*widget / dialog / card / row / canvas / pill — the whole radius system, so a theme can go angular (Graphite drops 20px → 3px)
--font-displaywith --display-track / --display-case: Caprasimo in Warm, tracked uppercase mono in the angular themes
--trace-1…6the trace cycle; 1 and 2 always alias the theme's two accents

Each theme also carries its own texture, voice and icon weight, all as tokens: --chrome-grad / --surface-grad / --well-grad / --accent-grad (Warm: none — flat and warm; Graphite: a faint top sheen, 3px scanlines in the wells, a vertical cyan fill on active controls; Neon: a magenta wash on the chrome, scanlines plus a floor bloom in the wells, a magenta-to-violet diagonal on fills), --cursor-glow / --chip-glow / --edge-lit for the bloom on the cursor line, filled chips and widget top edges, and --icon-stroke / --icon-cap so one Lucide set reads round-and-heavy in Warm (2.75, round) and thin-and-square in the angular themes (2 / 1.6, square). Display voices: Caprasimo (Warm), a condensed technical face (Graphite: Bahnschrift → Avenir Next Condensed → Arial Narrow), wide-tracked mono (Neon) — all platform faces, nothing fetched at runtime beyond the two the system already loads.

A fourth theme is a copy of one block with new values. The rules that hold across all of them: two accents, sage/mint for agreement, accent for attention, no red, mono for machine strings.

The rotor pane

A three.js canvas is a widget like any other: same .widget-head, same --ink-well stage, same theme tokens — the accent drives the rotor index mark and the LED colour, so the pane restyles with the rest of the app. Geometry in the mockup is a stand-in traced from board photos and says so on its face (stand-in mesh). Replacing it with the exported assembly is a loadGLTF() swap; the model must carry named nodes board · rotorA · rotorB · ledRing · led_*. STEP cannot be loaded directly — export glTF/GLB from CAD, or tessellate with an OpenCascade wasm build.

The large rotor is the driven one; the small rotor is an encoder test target and nothing in telemetry drives it, so it stays put. Two drive modes, matching the plots: live integrates the reported speed at display rate — never a redraw per sample — and at cursor makes the pose a pure function of the cursor time, so scrubbing a fault in the plots scrubs the machine. Missing data holds the last pose and says so; it never interpolates.

The LED ring is driven, not decorated: 36 RGB LEDs on a closed ring at 10° pitch, with long silkscreen ticks at the quadrants. The firmware's pattern is position — one LED tracks mechanical angle — and that is the default; four alternates (comet, 6-step commutation, electrical angle, bargraph) stay in the pane as a switchable row for comparing behaviours. Every LED runs its target through a rise/fall filter (28 ms up, 85 ms down) so the arc smears the way a real diode does instead of strobing at frame rate, and each one pairs an emissive package with a flat additive disc on the PCB: without that spill an emissive box reads as white paint, not light. Status LEDs follow a different rule — rails solid, PD-FLT blinking only on fault, a heartbeat at the link rate — because they report state, not motion.

One consequence worth keeping: above roughly 200 rpm the arc is a uniform glow. That is what the bench looks like, so the pane keeps it and offers a jog speed for reading the pattern.

How to extend it

·A new widget type inherits .widget-head whole: Caprasimo title, mode segmented control, legend right, ⋯ last. That header is the family resemblance.
·Anything the device can refuse gets a budget meter before the action and a verbatim reason string after it. Never paraphrase firmware.
·Missing data is stated, never interpolated: no sample in neutral-700 in readouts and tables, a terracotta tick in the .gap-ribbon on plots.
·New state colours come from a ramp step, not a new hue. Two accents is the budget.
·Nothing animates except live data and the 10 Hz link dot. No transitions on layout, no easing on state changes — a moving instrument panel is a lying instrument panel.
open question for the views-spec pass

Four capabilities here have no spec to point at yet: workspace layout (widget create / drag / resize / persistence), the shared cursor time as app-level state, the table widget, and split axes. The paginated cursor readout in particular needs a rule for how signals group into scales — right now the mockup assumes one page per Y scale. The rotor pane adds one more: the ring is RGB, and nothing yet says what colour encodes. It currently takes the theme accent throughout.
